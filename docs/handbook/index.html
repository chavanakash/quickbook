02

Optimizing the Docker images

Multi-stage builds: build tools and tests live in early stages and never reach the image that runs.

Three stages in every Python Dockerfile

builderpython:3.11-alpine → creates /opt/venv and installs runtime packages
testbuilder + pytest + tests → RUN pytest -q. Build fails if a test fails.
runtime (default)fresh python:3.11-alpine + only /opt/venv and app/, non-root user 10001
services/*/Dockerfile
# ---- builder ----
FROM python:3.11-alpine AS builder
WORKDIR /app
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.txt .
# BuildKit cache mount: pip's downloads are reused across builds but never stored in the image
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt

# ---- test (CI runs: docker build --target test) ----
FROM builder AS test
COPY requirements-dev.txt .
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements-dev.txt
COPY pytest.ini .
COPY app ./app
COPY tests ./tests
RUN pytest -q

# ---- runtime (default target) ----
FROM python:3.11-alpine AS runtime
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 PATH="/opt/venv/bin:$PATH"
RUN adduser -D -u 10001 appuser
WORKDIR /app
COPY --from=builder /opt/venv /opt/venv
COPY app ./app
USER 10001
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--no-access-log"]

What each technique buys

TechniqueEffect
Alpine base for runtime~50 MB base instead of ~130 MB for python:3.11-slim
venv copied from builderOnly installed packages reach the image: no pip cache, no build leftovers, no tests, no pytest
requirements before codeLayer order: dependencies change rarely, code often. A code change reuses the cached pip install layer.
Cache mounts (--mount=type=cache)pip/npm downloads persist between builds outside the image, so re-installs don't re-download
.dockerignoreKeeps __pycache__, .venv, *.db, node_modules out of the build context
Non-root user (uid 10001) + nginx-unprivilegedKubernetes runAsNonRoot passes; a container escape lands as an unprivileged user
OCI labelsorg.opencontainers.image.revision stores the git commit inside each image

Parallel builds & BuildKit cache

Six images built three at a time, with tests first in every branch.

Two batches of three

flowchart LR
    S[Prepare] --> B1
    subgraph B1 ["Batch 1 · parallel"]
      a[auth-service]
      i[inventory-service]
      b[booking-service]
    end
    B1 --> B2
    subgraph B2 ["Batch 2 · parallel"]
      p[payment-service]
      t[ticket-service]
      f[frontend]
    end
    B2 --> P[Push all 6]

Each box runs docker build --target test, then the runtime build. failFast true: one failure stops its siblings.

Why batches and not all six at once

Docker Desktop has 4 GB of RAM. Six simultaneous builds (pip installs, an npm install, a Vite build) compete for memory and CPU; three at a time keeps the machine responsive and still roughly halves the wall-clock time.

The same thing in plain bash

Background each build with &, then wait for the batch before starting the next one:

bash
# test target first, then the runtime image, for one app
tb() {
  app=$1; ctx=services/$app; [ "$app" = frontend ] && ctx=frontend
  docker build --target test "$ctx" && \
  docker build -t "dockerizzz/quickbook-$app:$app-$BUILD_NUMBER" "$ctx"
}
batch() {
  for app in "$@"; do tb "$app" & done   # start all in the background
  wait                                   # block until the whole batch is done
}

BUILD_NUMBER=42
time batch auth-service inventory-service booking-service
time batch payment-service ticket-service frontend

In the Jenkinsfile

Jenkinsfile
stage('CI: Test & build batch 1') {
    failFast true
    parallel {
        stage('auth-service')      { steps { script { testAndBuild('auth-service') } } }
        stage('inventory-service') { steps { script { testAndBuild('inventory-service') } } }
        stage('booking-service')   { steps { script { testAndBuild('booking-service') } } }
    }
}
stage('CI: Test & build batch 2') { failFast true; parallel { /* payment, ticket, frontend */ } }

  current=$(kubectl -n quickbook get deployment $a -o jsonpath='{.spec.template.spec.containers[0].image}')

Why a StatefulSet for Postgres

A Deployment's pods are interchangeable and get random names. A database needs the same identity and the same disk after every restart: a StatefulSet gives postgres-0 its own PersistentVolumeClaim, which follows it wherever it is rescheduled.

Resources per pod

WorkloadCPU request / limitMemory request / limit
Python services (×10 pods)50m / 500m128Mi / 256Mi
frontend (×2)25m / 200m32Mi / 128Mi
Postgres100m / 1256Mi / 512Mi
wait-for-postgres (init)10m / 100m16Mi / 64Mi

Request = what the scheduler reserves on a node. Limit = the ceiling: above the memory limit the container is OOMKilled; above the CPU limit it is throttled.

Security context on every app pod

  • runAsNonRoot: true at pod level
  • allowPrivilegeEscalation: false and capabilities: drop: ["ALL"] per container
  • Prometheus scrape annotations on Python pods (prometheus.io/scrape, port 8000)

Health probes

How Kubernetes decides a pod is alive, ready for traffic, or still starting.

ProbeEndpointTimingIf it fails
initContainer wait-for-postgrespg_isready -h postgres loopuntil Postgres answersPod stays in Init:0/1. The app never starts against a missing DB.
startupProbeGET /healthevery 2 s, 30 tries = 60 sContainer restarted. Until it passes, liveness is paused.
livenessProbeGET /healthevery 10 s, 3 failuresContainer restarted (process is stuck)
readinessProbeGET /ready (runs SELECT 1)every 5 s, 3 failuresPod removed from the Service. Not restarted; traffic goes to healthy replicas.
Postgres readiness / livenesspg_isready -U postgres5 s / 10 sSame rules as above
frontendGET /nginx-health5 s / 10 sSame rules as above
Liveness vs readiness

/health only says "the process answers". /ready also checks the database. If Postgres goes down, restarting the app would not help, so liveness stays green and only readiness turns red. Tested on this cluster: with Postgres stopped, auth pods went 0/1 (no traffic) with 0 restarts, and recovered by themselves when Postgres came back.

Rolling updates & rollback

New versions replace old ones without dropping capacity.

every Deployment
replicas: 2
revisionHistoryLimit: 5          # old ReplicaSets kept for rollout undo
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0            # never fewer than 2 ready pods
    maxSurge: 1                  # 1 extra pod allowed during the update
topologySpreadConstraints:       # prefer one replica per worker
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway
Startold ✓ old ✓
Surgeold ✓ old ✓ new …
New readyreadiness passes, one old pod removed
Repeatold ✓ new ✓ new …
Donenew ✓ new ✓, 2 ready throughout

If a new pod never becomes ready, the rollout stops and the old pods keep serving. Jenkins' rollout status --timeout=180s then fails the build, and the rollback guard undoes it.

rollout commands
kubectl -n quickbook rollout status  deployment/auth-service
kubectl -n quickbook rollout history deployment/auth-service
kubectl -n quickbook rollout undo    deployment/auth-service               # previous version
kubectl -n quickbook rollout undo    deployment/auth-service --to-revision=3
kubectl -n quickbook rollout restart deployment/auth-service               # same version, pods replaced one by one
Known gaps

No preStop delay: a request can still arrive in the instant an old pod shuts down. No PodDisruptionBudget: kubectl drain could evict both replicas at once. Postgres is a single replica, so replacing its pod means a short database outage.

Latency explained

What "p95" means, and why one panel can't show more than one second.

Latency is how long a request takes, from arriving at the service to the response leaving it. An average hides slow requests, so we use percentiles:

TermMeaning
p50 (median)Half of requests were faster than this
p9595% were faster; the slowest 1 in 20 took at least this long
p9999% were faster; shows rare slow outliers

How Prometheus computes it

The services don't record each duration. They count requests into histogram buckets: "≤ 0.1 s", "≤ 0.5 s", "≤ 1 s", "anything". histogram_quantile(0.95, …) then finds the bucket where 95% of requests fall and interpolates inside it.

Bucket limit on this project

The per-endpoint histogram (http_request_duration_seconds, from prometheus-fastapi-instrumentator) only has buckets 0.1 · 0.5 · 1 · +Inf. Any request slower than 1 s lands in "+Inf", so the panel can never show more than 1 s. auth-service shows exactly "1 s" under load: that means "at least 1 s". A second histogram, http_request_duration_highr_seconds, has 21 finer buckets (but no per-endpoint label); switching the panel to it, or adding custom buckets, would show the real value.

Why auth-service is the slowest

Passwords are hashed with bcrypt, which is deliberately slow to make brute-forcing expensive. Every sign-up and sign-in burns CPU, and each auth pod is limited to 0.5 CPU. With 10 simulated users at once, requests queue. The other services stay under 0.5 s at p95.

Lessons from real incidents

Problems hit while building this, and how each was diagnosed.

Pods restarted on first deploy

Symptom
DB services: 1–2 restarts each
Cause
Postgres took ~40 s (volume + image + initdb); apps gave up after 30 s
Fix
wait-for-postgres initContainer; verified by stopping Postgres: 0 restarts

Grafana kept disappearing

Symptom
Traefik: "no available server"
Cause
lastState: OOMKilled at the 384Mi limit, loading a 30-panel dashboard
Fix
Limit raised to 768Mi; 0 restarts since

Jenkins couldn't use Docker

Symptom
permission denied … docker.sock
Cause
Socket is root:root 660; Jenkins runs as uid 1000
Fix
group_add: ["0"] instead of running Jenkins as root

Traefik would not start

Symptom
Caught in helm template before install
Cause
Traefik metrics default 9100 = node-exporter's port on the host network
Fix
Metrics on 9102

Multipass broken on this Mac

Symptom
"Remote release unreachable", then qemu-img crash
Cause
Bundled qemu-img segfaults (exit 139), reproduced by hand
Fix
Lima with Apple's Virtualization framework (--vm-type=vz)

Scripts couldn't find *.localhost

Symptom
nodename nor servname provided
Cause
Browsers resolve *.localhost themselves; macOS doesn't
Fix
Scripts connect to 127.0.0.1 and send the Host header

Docker Hub pulls failed

Symptom
401, then 429 "too many failed login attempts"
Cause
Docker Desktop signed in with a revoked token
Fix
Re-login; stop retrying while locked out

"configured" on every apply

Symptom
Secrets and StatefulSet always reported as changed
Cause
stringData and defaulted volumeClaimTemplates fields
Check
Generation stayed 1, values matched: harmless
