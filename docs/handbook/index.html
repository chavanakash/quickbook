Optimizing the Docker images

Multi-stage builds: build tools and tests live in early stages and never reach the image that runs.

Three stages in every Python Dockerfile

builderpython:3.11-alpine → creates /opt/venv and installs runtime packages
testbuilder + pytest + tests → RUN pytest -q. Build fails if a test fails.
runtime (default)fresh python:3.11-alpine + only /opt/venv and app/, non-root user 10001
services/*/Dockerfile
# ---- builder ----
FROM python:3.11-alpine AS builder
WORKDIR /app
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.txt .
# BuildKit cache mount: pip's downloads are reused across builds but never stored in the image
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements.txt

# ---- test (CI runs: docker build --target test) ----
FROM builder AS test
COPY requirements-dev.txt .
RUN --mount=type=cache,target=/root/.cache/pip pip install -r requirements-dev.txt
COPY pytest.ini .
COPY app ./app
COPY tests ./tests
RUN pytest -q

# ---- runtime (default target) ----
FROM python:3.11-alpine AS runtime
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1 PATH="/opt/venv/bin:$PATH"
RUN adduser -D -u 10001 appuser
WORKDIR /app
COPY --from=builder /opt/venv /opt/venv
COPY app ./app
USER 10001
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--no-access-log"]

What each technique buys

TechniqueEffect
Alpine base for runtime~50 MB base instead of ~130 MB for python:3.11-slim
venv copied from builderOnly installed packages reach the image: no pip cache, no build leftovers, no tests, no pytest
requirements before codeLayer order: dependencies change rarely, code often. A code change reuses the cached pip install layer.
Cache mounts (--mount=type=cache)pip/npm downloads persist between builds outside the image, so re-installs don't re-download
.dockerignoreKeeps __pycache__, .venv, *.db, node_modules out of the build context
Non-root user (uid 10001) + nginx-unprivilegedKubernetes runAsNonRoot passes; a container escape lands as an unprivileged user
OCI labelsorg.opencontainers.image.revision stores the git commit inside each image

Parallel builds & BuildKit cache

Six images built three at a time, with tests first in every branch.

Two batches of three

flowchart LR
    S[Prepare] --> B1
    subgraph B1 ["Batch 1 · parallel"]
      a[auth-service]
      i[inventory-service]
      b[booking-service]
    end
    B1 --> B2
    subgraph B2 ["Batch 2 · parallel"]
      p[payment-service]
      t[ticket-service]
      f[frontend]
    end
    B2 --> P[Push all 6]

Each box runs docker build --target test, then the runtime build. failFast true: one failure stops its siblings.

Why batches and not all six at once

Docker Desktop has 4 GB of RAM. Six simultaneous builds (pip installs, an npm install, a Vite build) compete for memory and CPU; three at a time keeps the machine responsive and still roughly halves the wall-clock time.

The same thing in plain bash

Background each build with &, then wait for the batch before starting the next one:

bash
# test target first, then the runtime image, for one app
tb() {
  app=$1; ctx=services/$app; [ "$app" = frontend ] && ctx=frontend
  docker build --target test "$ctx" && \
  docker build -t "dockerizzz/quickbook-$app:$app-$BUILD_NUMBER" "$ctx"
}
batch() {
  for app in "$@"; do tb "$app" & done   # start all in the background
  wait                                   # block until the whole batch is done
}

BUILD_NUMBER=42
time batch auth-service inventory-service booking-service
time batch payment-service ticket-service frontend

In the Jenkinsfile

Jenkinsfile
stage('CI: Test & build batch 1') {
    failFast true
    parallel {
        stage('auth-service')      { steps { script { testAndBuild('auth-service') } } }
        stage('inventory-service') { steps { script { testAndBuild('inventory-service') } } }
        stage('booking-service')   { steps { script { testAndBuild('booking-service') } } }
    }
}
stage('CI: Test & build batch 2') { failFast true; parallel { /* payment, ticket, frontend */ } }

Why a StatefulSet for Postgres

A Deployment's pods are interchangeable and get random names. A database needs the same identity and the same disk after every restart: a StatefulSet gives postgres-0 its own PersistentVolumeClaim, which follows it wherever it is rescheduled.

Request = what the scheduler reserves on a node. Limit = the ceiling: above the memory limit the container is OOMKilled; above the CPU limit it is throttled.

Health probes

How Kubernetes decides a pod is alive, ready for traffic, or still starting.

ProbeEndpointTimingIf it fails
initContainer wait-for-postgrespg_isready -h postgres loopuntil Postgres answersPod stays in Init:0/1. The app never starts against a missing DB.
startupProbeGET /healthevery 2 s, 30 tries = 60 sContainer restarted. Until it passes, liveness is paused.
livenessProbeGET /healthevery 10 s, 3 failuresContainer restarted (process is stuck)
readinessProbeGET /ready (runs SELECT 1)every 5 s, 3 failuresPod removed from the Service. Not restarted; traffic goes to healthy replicas.
Postgres readiness / livenesspg_isready -U postgres5 s / 10 sSame rules as above
frontendGET /nginx-health5 s / 10 sSame rules as above
Liveness vs readiness

/health only says "the process answers". /ready also checks the database. If Postgres goes down, restarting the app would not help, so liveness stays green and only readiness turns red. Tested on this cluster: with Postgres stopped, auth pods went 0/1 (no traffic) with 0 restarts, and recovered by themselves when Postgres came back.

Rolling updates & rollback

New versions replace old ones without dropping capacity.

every Deployment
replicas: 2
revisionHistoryLimit: 5          # old ReplicaSets kept for rollout undo
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0            # never fewer than 2 ready pods
    maxSurge: 1                  # 1 extra pod allowed during the update
topologySpreadConstraints:       # prefer one replica per worker
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway
Startold ✓ old ✓
Surgeold ✓ old ✓ new …
New readyreadiness passes, one old pod removed
Repeatold ✓ new ✓ new …
Donenew ✓ new ✓, 2 ready throughout

If a new pod never becomes ready, the rollout stops and the old pods keep serving. Jenkins' rollout status --timeout=180s then fails the build, and the rollback guard undoes it.

rollout commands
kubectl -n quickbook rollout status  deployment/auth-service
kubectl -n quickbook rollout history deployment/auth-service
kubectl -n quickbook rollout undo    deployment/auth-service               # previous version
kubectl -n quickbook rollout undo    deployment/auth-service --to-revision=3
kubectl -n quickbook rollout restart deployment/auth-service               # same version, pods replaced one by one
Known gaps

No preStop delay: a request can still arrive in the instant an old pod shuts down. No PodDisruptionBudget: kubectl drain could evict both replicas at once. Postgres is a single replica, so replacing its pod means a short database outage.

Latency explained

What "p95" means, and why one panel can't show more than one second.

Latency is how long a request takes, from arriving at the service to the response leaving it. An average hides slow requests, so we use percentiles:

TermMeaning
p50 (median)Half of requests were faster than this
p9595% were faster; the slowest 1 in 20 took at least this long
p9999% were faster; shows rare slow outliers

How Prometheus computes it

The services don't record each duration. They count requests into histogram buckets: "≤ 0.1 s", "≤ 0.5 s", "≤ 1 s", "anything". histogram_quantile(0.95, …) then finds the bucket where 95% of requests fall and interpolates inside it.

Bucket limit on this project

The per-endpoint histogram (http_request_duration_seconds, from prometheus-fastapi-instrumentator) only has buckets 0.1 · 0.5 · 1 · +Inf. Any request slower than 1 s lands in "+Inf", so the panel can never show more than 1 s. auth-service shows exactly "1 s" under load: that means "at least 1 s". A second histogram, http_request_duration_highr_seconds, has 21 finer buckets (but no per-endpoint label); switching the panel to it, or adding custom buckets, would show the real value.

Why auth-service is the slowest

Passwords are hashed with bcrypt, which is deliberately slow to make brute-forcing expensive. Every sign-up and sign-in burns CPU, and each auth pod is limited to 0.5 CPU. With 10 simulated users at once, requests queue. The other services stay under 0.5 s at p95.

Load testing in plain words

Think of the app as a small restaurant: customers arrive, read the menu, order, and wait for the kitchen.

We test for three reasons: to find how many users the site can handle, to see how it breaks when it can't, and to prove a fix works.

WordRestaurantIn QuickBook
Arrival rate λ (lambda)Customers walking in per secondNew users per second. λ = 4 → 4 new users every second on average
Think timeTime reading the menuTime on a page before the next click (e.g. ~8 s on search)
Service timeTime to cook one dishServer work for one request (a login ≈ 0.53 s)
CapacityMost dishes per secondMost logins per second (≈ 3.8 before the fix)
QueueOrders waiting for the chefRequests waiting for CPU / a thread
LatencyOrder → foodRequest → response
GoodputDishes served correctly per secondSuccessful requests per second
The kneeWhere waiting suddenly explodesλ ≈ 4 before the fix

p50, p95, p99 instead of the average

Line up 100 customers from fastest to slowest. p50 is customer #50 (half were faster), p95 is #95 (only 5 waited longer), p99 is #99.

Why not the average?

If 95 people wait 1 minute and 5 wait 60 minutes, the average is about 4 minutes, which describes nobody. p95 says "1 in 20 waited at least this long": that is who complains.

Open vs closed model

Closed (unrealistic)

Always exactly 10 users. When the site slows down they simply click more slowly, so load drops exactly when the site struggles, hiding the problem.

Open (what we use)

New users keep arriving at rate λ no matter how slow the site is, like real customers who can't see the kitchen. This exposes the real breaking point.

Kinds of test

TestShapeQuestion
SmokeTiny, 30 sDoes the test itself work?
LoadSteady normal trafficAre we healthy on a busy day? (SLO pass/fail)
StressRamp up past the limitWhere and how does it break?
SpikeSudden burst, then normalDoes it recover?
SoakNormal traffic for hoursSlow leaks (memory, disk)?

SLO (Service Level Objective) = the pass/fail target agreed before testing. Ours: errors < 1%, login p95 < 2.5 s, every other page p95 < 0.5 s.

Distributions without the maths

A distribution is just a recipe for random numbers: "around 8 seconds, sometimes 4, sometimes 20".

Why random at all?

Variation is what creates queues. If a customer arrived exactly every 15 s and every dish took exactly 10 s, nobody would ever wait. Queues form because sometimes 3 customers arrive together. Fixed numbers make a test far too optimistic.

Seed: the starting number for the computer's random numbers. The same seed gives the same "random" users, so --seed 42 before and after a change means both runs faced identical customers: a fair comparison.

Exponential: gaps between arrivals

People don't coordinate when they visit, so arrivals are random and independent. One number describes it: the average gap (1 ÷ λ). Most gaps are short, a few are long, and short gaps cluster into bursts. Arrivals made this way are called a Poisson process.

At λ = 2 users/s: average gap 0.5 s, but 63% of gaps are shorter (shaded), about 14% are longer than 1 s, and now and then there is a 1.5 s silence followed by a burst.

k6 is different

k6's arrival-rate modes space users evenly (exactly every 0.67 s at 1.5/s). No bursts, so slightly kinder to the system than real traffic. Our Python generator and the model use real Poisson arrivals.

Lognormal: time spent on a page

Most people take about the same time and a few take much longer (phone call, comparing prices). Nobody takes negative time, and the tail stretches right. Two numbers describe it:

  • median: the middle value, half of users faster, half slower
  • σ (sigma): how spread out people are

Search page, median 8 s, σ 0.6: half of users leave within 8 s (shaded). The average is 9.6 s, pulled up by the slow ones. The slowest 10% stay longer than 17 s.

time_scale: fast-forward

A real visit lasts about 90 s. time_scale = 0.25 shrinks every think time to a quarter: the restaurant at 4× speed. It does not change the arrival rate or the server work per request, so logins per second stay the same; only the number of users on the site at once changes.

The user journey & the load generator

Each fake user rolls dice on every page to decide what to do next.

flowchart LR
    L[landing] --> G[login] --> S[search]
    S -->|50% search again| S
    S -->|40% book| P[passengers] --> Y[payment]
    S -->|10% leave| X((left))
    Y -->|81% paid, gets PDF| T[ticket] --> D((booked))
    Y -->|9% paid, no PDF| D
    Y -->|6% card declined, retry| Y
    Y -->|4% declined, gives up| X

A Markov chain: the next page depends only on the current one. The percentages leaving each page must add up to 100%.

How scripts/load_model.py works

1. Arrivedraw an exponential gap, wait, start a user (rate λ per stage)
2. Walkeach user runs on its own: request, think (lognormal), roll the dice for the next page
3. Recordevery request: step, time, latency, status, saved to a CSV
4. Judgeper-stage and per-page p50/p95/p99, Little's Law check, SLO PASS/FAIL (exit code 2 on FAIL)
ProfileShape
smoke30 s at 0.5 users/s
load-steady1 min warm-up, then 5 min at 1.5 users/s, with SLOs
stress-rampλ = 1 → 2 → 4 → 6 → 8 → 10 users/s, 60 s each
spike1/s, a 30 s burst at 10/s, then 1/s

Little's Law, the sanity check

Users on the site = arrival rate × time each spends. 2 users/s × 30 s each = 60 people on the site at once. It always holds, so if the measured number is far off, something in the test is wrong.

Why login was the weak point

Passwords are hashed with bcrypt, which is deliberately slow so stolen password databases take years to crack. Each login costs about 0.26 CPU-seconds (a search costs 0.004).

capacity = pods × CPU limit ÷ CPU per login = 2 × 0.5 ÷ 0.26 ≈ 3.8 logins/s

That arithmetic, from light-load numbers alone, matched the measured knee.

How "slow" became "down"

CPU fullbcrypt uses the whole 0.5-core limit
Probes stuck/health waits in the same queue, times out after 1 s
Readinesspod removed from traffic → 502s
Liveness"dead" pod restarted mid-rush → less capacity
Cascadethe other pod takes everything, and fails too

Restaurant version: the kitchen is so busy the chef can't answer the manager's phone, so the manager sends the chef home in the middle of dinner.

Steady load test (1.5 users/s)

All SLOs passed, 0 errors, 0 restarts. But login p95 was 2.23 s against a 2.5 s target: a thin margin. auth was only ~33% busy, yet throttled in 61% of CPU periods: the 0.5-core limit pauses every bcrypt hash, roughly doubling each login's time.

Survivorship bias

At λ = 8 the live p95 briefly read 50 ms. Only because logins were failing: the only successes left were fast searches. Always read latency next to the error rate.

The capacity model (simulation)

A pretend copy of the system that runs a full stress test in about a second, without touching the cluster.

Built with SimPy, a Python library for discrete-event simulation: it doesn't run the app, it moves pretend users and requests through pretend servers as pretend time passes.

What's inside

PieceBehaves like
UsersSame exponential arrivals, Markov journey and lognormal think times as the load generator
Pods: processor sharingOne chef stirring up to 40 pots in rotation (uvicorn's thread pool). 1 pot gets full attention; 40 pots each get 1/40th, so every dish takes 40× longer. Extra orders wait in line.
CPU limitA 0.5-core limit = the chef works at half speed
Probes & restartsReadiness removes busy pods, liveness restarts them; CrashLoopBackOff waits 10 s, 20 s, 40 s … between restarts
TimeoutsThe gateway gives up after 30 s, but the server keeps cooking the abandoned dish (wasted work)

Load shedding, waiting roomOptional: fast "busy" rejections; cap on users admitted to the site

At very light load nothing queues, so request time ≈ pure work. Login took 0.53 s on a 0.5-core limit → work = 0.53 × 0.5 = 0.263 CPU-seconds. calibrate.py does this for every page.

Prediction committed before testing

The model's forecast for the fixed system was committed to git before deployment, so the timestamp proves it came first: 0 errors up to 10 users/s, login p95 0.55 s at normal load (was 1.4 s), 0 restarts, HPA to 3 pods at ~135 s and 4 pods at ~150 s.

Every release now passes a performance gate

flowchart LR
    A[git push] --> B[unit + model tests] --> C[build 6 images] --> D[deploy] --> E[smoke test]
    E --> F{"k6 gate
90 s at 1.5 users/s
SLO thresholds"}
    F -->|pass| G([release stays])
    F -->|fail| H([automatic rollback])

k6 runs as a Kubernetes Job on the control-plane node, so the load generator never shares CPU with the app or the laptop. Its metrics go to Prometheus (remote write). Seven alert rules turn the findings into operations: auth CPU throttled, login SLO breach, error rate, load shedding active, HPA at maximum, readiness flapping, restarts under load.

A real metastable failure

The first k6 gate, run on the old system just after the stress tests, failed even at normal load: auth pods had restarted 7 times and sat in CrashLoopBackOff, so one pod at a time carried normal traffic and kept being killed. A system that stays broken after the trigger has gone is a metastable failure, a classic pattern behind large outages. The gate caught it.

When the laptop sleeps, the cluster freezes

The first gate on the fixed system showed 0 errors in 917 requests and login p95 0.78 s, yet failed with an 8-minute sign-up "p95". Cause: the Mac went into idle sleep, freezing all three VMs; on wake Lima stepped every clock forward by the same 8m24s, and in-flight requests looked 8 minutes long. The rollback still worked exactly as designed. Fix: keep the Mac awake during tests (caffeinate -i).

Status

Next measurements: three stress runs on the fixed system (same seeds as the baseline), compared with the model's prediction in one before/after chart; a deliberate regression (bcrypt cost 15) to show the gate stopping it; and a stress-then-gate run to show the fixed system recovers.
